# i18n

## Translator class

`Kaly\Text\Translator` is a small translator that supports a subset of the Symfony
translation features (nested ids, plural forms, `{}` and `%param%` placeholders) and
uses PHP files as its storage format.

```php
use Kaly\Text\Translator;

$translator = new Translator('en');
$translator->translate('hello.world');
```

Catalog files are named `{domain}.{locale}.php` and live in the registered paths:

```php
// messages.en.php
return [
    'hello' => [
        'world' => 'Hello world',
    ],
];
```

## Locale handling

The locale can come from the route (a locale prefix handled by the `ClassRouter`) or
from the `Accept-Language` header.

`RequestDispatcher` applies the locale before the controller runs:

- it reads the route locale and sets it through `Translator::setCurrentLocale()`;
- it exposes the resolved locale as a request attribute under
  `RequestDispatcher::ATTR_LOCALE_REQUEST` (`locale`), which is the same key as
  `Translator::ATTR_LOCALE_REQUEST`.

When no locale is imposed by the route, `Translator::setLocaleFromRequest()` picks the
best match from the request headers using `getPreferredLanguage()`:

```php
$translator->setLocaleFromRequest($request, ['en', 'fr']);
```

The locale is stored on the request as an attribute so downstream code (and the
translator itself) can rely on it.

## Caching

In production (`APP_DEBUG` disabled), `App::updateDefinitions()` configures the
translator cache directory to `temp/translator`. Catalogs are then written to that
directory and reloaded from it, avoiding filesystem lookups on each request.

In debug mode no cache is configured, so template/catalog changes are picked up
immediately.

## Helpers

The optional `src/_functions/global.php` helpers provide a `t()` shortcut that resolves
the translator from the container. They are not autoloaded: require the file or define
your own helper if you want it.
